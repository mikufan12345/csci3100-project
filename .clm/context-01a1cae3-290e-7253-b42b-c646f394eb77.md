## `TenantScopedController` — a "concern"

In Rails, a controller is a class that handles one kind of page/action (e.g. "list games", "create game"). A **concern** is just a bundle of shared methods you can mix into many classes — think of it as a reusable snippet of behavior.

`TenantScopedController` would be a small file containing the tenancy boilerplate, and every real controller "includes" it:

```ruby
# app/controllers/concerns/tenant_scoped_controller.rb
module TenantScopedController
  extend ActiveSupport::Concern

  included do
    before_action :require_studio
  end

  private

  # Runs before EVERY action in any controller that includes this:
  def require_studio
    return unless user_signed_in?          # not logged in? Devise redirects to login
    @current_studio = current_user.studio  # grab "which studio does this user belong to"
  end

  # The one-liner every controller uses instead of raw database lookups:
  def scoped_find(model)
    # "find this record, but ONLY within my studio"
    @current_studio.game_projects.where(...).find(params[:id])  # (simplified)
  end
end
```

And a real controller shrinks to:

```ruby
class GameProjectsController < ApplicationController
  include TenantScopedController

  def create
    game = scoped_find_or_new(GameProject)   # can never escape the tenant
    game.title = params[:title]
    game.save
  end
end
```

**Why this shape matters:** the danger in multi-tenant apps is one careless line somewhere — `GameProject.find(params[:id])` — that lets a Studio B user grab a Studio A record. If tenancy lives in *one* file that every controller goes through, there's one place to get it right and one place to audit. That's the entire point, and it's the rule your AGENTS.md already declares ("do not scatter `where(studio:)` by hand").

## `authorize_role!` — the check that stops the wrong *kind* of user

Tenancy answers "whose data is this?" Roles answer "are you allowed to do this *action*?" Even inside the correct studio, a playtester shouldn't be able to publish a rulebook. So:

```ruby
def authorize_role!(allowed)
  unless current_user.roles.include?(allowed)
    raise AccessDenied          # → the app responds 403 "forbidden" and stops
  end
end
```

Used like: `authorize_role!(User::STUDIO_ADMIN)` at the top of a publish action.

## The `!` — your specific question

Ruby has a community convention: a method name ending in **`!` (bang) means "this one can raise an exception / be destructive"** — the "loud, stops everything" variant. Contrast the pairs you'll see everywhere:

- `find(id)` vs `find(id)!` → without `!`: returns `nil` if missing; with `!`: raises an error if missing
- `authorize_role!` → "check the role, and **halt with a 403 if it fails**" — it's a guard, not a question

So the `!` is just a hint to the reader: *this method doesn't return normally when something's wrong; it explodes loudly on purpose.* It's pure convention — Ruby works fine without it — but Rails follows it religiously, so `authorize_role!` is the idiomatic name for exactly this "check or crash" behavior.

That's the whole pair: **one concern that fences every query inside the studio, one guard that fences every action behind the right role.** Both together are maybe 60 lines of code. Want me to go build them?
